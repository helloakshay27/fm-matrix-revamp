Chart Calculation & Instrumentation Reference

SmartSecure · Gatekeeper & Security Analytics Dashboard — Developer Handoff

Product: SmartSecure residential-society gatekeeper/security app / Lockated GoPhygital.work

Purpose: The authoritative, implementable definition of every chart/metric shown in the SmartSecure analytics wireframe — the instrumentation contract (events + properties) and the exact math for each metric — so that mobile, backend and data engineers can wire the dashboard to a live PostHog project instead of the seeded/illustrative sample data it ships with today.

Source: Reverse-engineered verbatim from SmartSecure_Dashboard_v1_FM_structure.html (the FM-Matrix-aligned wireframe build) — its <script> section, KPI_INFO formula dictionary, modulesList[], workflows[] and inline disclosure comments are the ground truth for every metric definition below.

Companion artefact: SmartSecure_PostHog_Events.xlsx — "PostHog Events" sheet (180 events across 38 categories) plus a "Common Stamps (all events)" sheet documenting the 15 context properties stamped on every event. Unlike Rustomjee Circle, there is no live PostHog project behind SmartSecure at all — this catalogue is a developer-authored specification of intended instrumentation (it reads at the level of exact code mechanics: provider init() vs. screen initState(), .catchError handlers, PlatformException, NavigatorObserver), not a live/firing analytics feed.

How to read this document: Section 6 defines the raw events, the context properties stamped on every event, the session definition, and the notation — mirroring the companion FM Matrix, Runwal Connect, Panchshil Connect, Panchshil Pulse and Rustomjee Circle Chart Calculation & Instrumentation References so all six documents share one vocabulary. Section 7 then expresses every KPI tile, chart and table on every page of the dashboard as a formula over those events. Every metric in Section 7 traces back to Section 6. Event names and module/bucket groupings taken directly from the SmartSecure PostHog Events sheet are marked "as-is"; metrics whose calculation is not explicit in the spreadsheet and has been proposed to fit the surrounding naming style are marked "proposed".

Scope note — read this before anything else: there is NO live PostHog project, GA4 feed, or Crashlytics feed behind SmartSecure at all — the same situation as Panchshil Pulse, and different from Rustomjee Circle, whose catalogue documents an actually-live, currently-firing PostHog project. Every volume, rate, percentage and trend line in the shipped wireframe is seeded pseudo-random sample data (mulberry32/hashStr, keyed by chart name + device filter), generated only so the wireframe reads like a populated dashboard. This document does not change any number in the dashboard; it specifies what a real PostHog event stream — using the event names already documented in SmartSecure_PostHog_Events.xlsx — would need to look like to replace every seeded number with a computed one. The event names, module names and bucket structure below ARE real (in the sense of being the intended, documented instrumentation); the numbers are not, and nothing is flowing into PostHog today.

Signal Type note: SmartSecure's catalogue uses a two-way Event / Success / Failure typing rather than the View / Action / Failure convention used in the Rustomjee/Panchshil family of catalogues. There is no explicit "View" type — a screen load is typed Success (e.g. splash_screen_viewed, staff_list_viewed), and "Event" covers both navigation taps and the "before the API call" marker events (e.g. login_attempted, visitor_create_attempted). Section 6.2's Tag column calls out this distinction wherever it affects a metric's formula.

Revision note — design-team Figma screens reviewed post-initial-build: after this document and the wireframe were first built, the design team shared Figma exports of the real visitor-registration screens (two "FM Matrix" zip exports, despite the name, containing SmartSecure design material). Those screens reveal a 5-step visitor registration wizard, of which only step 1 is currently represented in SmartSecure_PostHog_Events.xlsx. This revision documents that gap against the Visitor Creation workflow (§7.3.0, Visitor Ops bucket) and adds a new §7.3.0b listing proposed (unconfirmed) event names for the 3 missing steps, mirroring the wireframe's own "proposed" workflow cards added for the same reason.

6. Instrumentation & Event Taxonomy (authoritative)

All metrics in Section 7 are computed from the events below. PostHog is assumed, consistent with the dashboard's own footer note. SmartSecure is a mobile-first gatekeeper/security app (Android tablets at society gates, per the catalogue's device-approval flow); screen views are explicit custom events (e.g. *_list_viewed, *_screen_viewed), not $pageview-style browser autocapture.

6.1 Context properties (stamped on every event)

Per the catalogue's own "Common Stamps (all events)" sheet, these are confirmed real on every event, not proposed: Device & app — app_version, build_number, platform (android|ios), os_version, device_model, is_physical_device. Identity — user_id ("none" if not logged in), lockated_user_id (secondary/legacy identifier from the Lockated backend). Tenant — society_id (which housing society/complex), device_society_id (society tied to the device's own registration — can differ from society_id, useful for catching device-misconfiguration bugs), building_name (human-readable). Role & location — role (gatekeeper | supervisor | admin; "none" if not resolved yet), gate_name (which physical gate the device is stationed at), screen (the app screen the event fired from). Tag: as-is for all of the above — this is the one property list in this whole document family that is confirmed rather than proposed, since it is drawn directly from the catalogue's own documentation rather than reverse-engineered from a wireframe.

Full 180-event / 38-category catalogue: the table above is a representative slice covering every workflow funnel in Section 7.3.0 plus the bookkeeping-only modules; it is not the complete event list. The authoritative full list is SmartSecure_PostHog_Events.xlsx itself (Category, Event Name, What It Does, Key Properties/Parameters, Signal Type columns) — engineers should treat that spreadsheet, not this document, as the source of truth for any event not named above.

Signal Type column (Event / Success / Failure) is a real, confirmed taxonomy from the catalogue itself, not proposed: Event = an action fired before its outcome is known (e.g. an "attempted" marker, or a navigation tap); Success = the action completed or a screen loaded successfully (there is no separate View type — screen loads are typed Success, e.g. splash_screen_viewed, staff_list_viewed); Failure = validation failed, an API call errored, or a permission/exception occurred. This maps directly onto the Engagement Rate and Feature Interaction Rate calculations in Section 7.1 — a session with only Success-typed screen loads and no Event-typed action is a bounce.

6.3 Person & Group properties

Person: user_id (person identifier; "none" if not logged in), lockated_user_id (secondary/legacy identifier), role (gatekeeper|supervisor|admin), $first_seen (first event timestamp — powers Day 1/7/30 Retention, New-vs-Returning), plus context properties. Group (Society): society_id, building_name, device_society_id (for cross-checking device-to-society misconfiguration). Group (Portfolio/Account): total_registered_gate_staff, licensed_modules[] (the 17-module PostHog Events catalogue). Tag: as-is for user_id/role/society_id/building_name (confirmed via the "Common Stamps" sheet); total_registered_gate_staff and licensed_modules[] are proposed to complete the taxonomy in the FM Matrix style — the catalogue documents event names and payload shape but not an explicit roster/licensing schema.

BOOKED_HOMEBUYERS (variable name kept identical across the shared JS engine) = 2,500 (ILLUSTRATIVE — hard-coded placeholder constant in the dashboard JS, functioning here as the "registered gate staff/admins across all societies" ceiling the Active Users line is scaled against, not a real/confirmed figure. In production this must be sourced live from the society-management/CRM system that provisions gate-staff accounts, the direct analogue of Rustomjee Circle's BOOKED_HOMEBUYERS and Runwal Connect's booked_homebuyers_count.

6.4 Session definition & derived fields

A session = a user's maximal event sequence with less than 30 minutes of inactivity between events (PostHog default, same convention as FM Matrix). Materialised per session_id:

•  session_duration_s = ts(last event in session) − ts(first event in session)

•  screen_view_count = count(Success-typed screen-load events in session, e.g. *_list_viewed, *_screen_viewed — SmartSecure has no separate View type, so screen loads are Success-typed)

•  action_count = count(Event-typed action events in session, e.g. *_attempted, *_tapped — excluding app_launched itself)

•  is_bounce = 1 if (screen_view_count ≤ 1 AND action_count = 0) else 0 — matches KPI_INFO's Bounce Rate definition ("only app_launched/home_tab_viewed and no further interaction")

•  entry_screen = screen property of the first Success-typed screen-load event in the session (as-is; powers F-entry, "Top entry screens", §7.3)

•  platform, app_version, gate_name, society_id

exit_screen (last screen-load event in a session) is not used by any metric in this document, consistent with FM Matrix's Workflow Usage layer, which does not carry a Top Exit Screens table.

6.5 Notation used in Section 7

Scope S = events where society_id ∈ viewer's permitted society scope AND is_physical_device = true (excludes emulator/simulator test traffic). (Single-tenant, single-admin dashboard — the wireframe note confirms "shows only one society's own gate staff, visitors and vehicles; no cross-society data.")

Period P = the selected date-range filter (default "Last 30 days", editable via the filterbar date pickers); P⁻ = the immediately preceding equal-length window ("Previous period" toggle, on by default).

distinct(x) = count of distinct values; count(ev) = number of events named ev.

users = distinct(user_id); sessions = distinct(session_id). All computed over S ∩ P unless stated. dev(d) = filter predicate platform = d, applied when the dashboard's All/iOS/Android device toggle is set to d (dashboard constant devFactor: ios=0.58, android=0.42, all=1 — a placeholder stand-in for the real per-platform share until live data exists; SmartSecure runs primarily on Android gate tablets in practice, so the real split is expected to skew heavily Android once live).

module = one of the 17 real modules mapped from the SmartSecure PostHog Events sheet (as-is): Home, Splash & Device Approval, Authentication, Visitor Management, Staff Management, Profile & Staff Verification, Notifications, Member Vehicle, Visitor Vehicle, QR Scanner / Gate Entry, Setup, Patrolling, Goods Outward, History Filter (shared), Help Center, Shared Utilities, App Lifecycle. Six of these (Home, Authentication, Notifications, Help Center, History Filter (shared), Shared Utilities) plus App Lifecycle carry no user-facing workflow — see §7.3's introductory note.

flow_key = one of the 19 real workflow-bearing modules' workflows in workflows[] (as-is), each with a bucket (Access & Device | Visitor Ops | Staff Ops | Vehicle Ops | Security & Assets | Configuration) and an ordered steps[] array of real event names verified verbatim against SmartSecure_PostHog_Events.xlsx — the exact catalogue is reproduced in Section 7.3.0. A further 3 workflows (proposed:true in the wireframe's workflows[] array) use proposed, unconfirmed event names that do NOT appear in the spreadsheet — these are reproduced separately in Section 7.3.0b and excluded from every "19 real workflows" count in this document.

7.3 Workflow-Usage Packs (Workflow Usage page)

Home, Authentication, Notifications, Help Center, History Filter (shared) and Shared Utilities are excluded from this layer in their entirety: Home's events (home_tab_viewed, home_refresh_triggered, home_menu_tile_tapped, plus the visitor-pass OTP and QR-scan-failure sub-events) are lateral navigation/dashboard impressions with no single directional funnel of their own; Authentication is a single login/logout action pair rather than a multi-step process; Notifications, Help Center, History Filter and Shared Utilities (document preview/download, camera capture) are cross-cutting utility surfaces reused across other modules' real workflows rather than funnels in their own right. 7.4 Access & Tiering — out of scope

SmartSecure's dashboard does not implement a tiered access model analogous to the companion FM Matrix reference's T1 (Site) / T2 (Regional) / T3 (Management) structure — it is a single-tenant, single-admin gate view (per the wireframe note: "Single-tenant gate-admin view — shows only one society's own gate staff, visitors and vehicles"). Access tiering is therefore treated as out of scope for this reference.

If SmartSecure or Lockated later introduces role-scoped views — for example, a per-gate supervisor view vs. a portfolio-wide multi-society management view, mirroring FM Matrix's site/region/org scopes — that tiering model, and which of the metrics in Sections 7.1–7.3 each tier would see by default vs. on drill-down, would be a natural addition to a future revision of this document.

This dashboard also has no App Stability / Crash Analytics page, by scope decision matching Runwal Connect's and Panchshil Pulse's 3-layer treatment rather than Panchshil Connect's bespoke 4th layer. Unlike Rustomjee Circle's App Health & Errors category (which is Crashlytics-cross-verified), SmartSecure's catalogue has no dedicated crash/diagnostics category at all — but it does carry Failure-typed events throughout nearly every category (63 of the 180 documented events are Failure-typed, covering validation failures, API failures, and permission/exception failures). Should a future revision add a reliability/error-rate layer, these 63 Failure-typed events, grouped by category, would be the starting point — see the companion Panchshil Connect reference for the proven pattern of building such a layer.
